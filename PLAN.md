# Агент-стажёр: итоговый план и требования

## 1. Цель
AI-агент на базе opencode (Windows): наблюдает за действиями пользователя, запоминает процедуры в долговременную память, обобщает на аналогичные задачи (сервер1 → сервер2), пишет человекочитаемые инструкции, переиспользует решения, при неудаче модифицирует и обновляет память.

## 2. Архитектура
- git-репо `agent-memory/` — хранилище памяти;
- скилл opencode — оркестратор (ретривал, планирование, стоп-вопросы);
- PowerShell-скрипты — исполняющий слой (verify, confidence, stats, index);
- плагин `guard.ts` — хуки `tool.execute.before/after`: политики, санитизация, маскирование секретов;
- permission-правила opencode + Execution Policy — жёсткие границы.

## 3. Структура памяти
```
agent-memory/
├─ procedures/<id>.yaml   — определение: schema_version, параметры (имя, тип, пример),
│                           шаги, criteria (exit_code|regex|http_status), dependencies,
│                           tags, owner, status (active | non-working)
├─ state/<id>.yaml        — мутабельное: hosts: {host: {runs, ok, last_result}}
├─ instructions/<id>.md   — человекочитаемая инструкция; версии через git, старые
│                           помечаются «нерабочее решение», не удаляются
├─ index.json             — производный артефакт (keywords, теги, TF-IDF);
│                           пересобирается scripts/index.ps1 (единственный писатель)
├─ golden_set.json        — 30–50 размеченных запросов для метрик ретривала
├─ telemetry/*.jsonl      — session_id, процедура, версия, модель, шаги, статус,
│                           токены, время, P-уровень
└─ lockfile               — блокировка + атомарная запись (temp+rename)
```

## 5. Итоговые требования к агенту
1. Перед любой задачей — обязательный поиск похожих в памяти и переиспользование найденного.
2. Неоднозначность — стоп-вопрос, никаких догадок.
3. При неудаче решения — модификация; если модификация помогла — сохранить новую версию, предыдущую пометить «нерабочее решение», не удалять.
4. Креды: спрашивать пользователя; при хранении — шифрованно (age/sops) или менеджер паролей; LLM видит только REDACTED.
5. Исполнение только по уровням P0/P1/P2: P0 — read-only по allowlist при высокой уверенности, критерий успеха и лимиты заданы; классификатор обязан иметь класс uncertain и при сомнении идти вверх.
6. Критерии успеха — декларативные, машинно проверяемые, согласуются с пользователем.
7. Захват с параметризацией: LLM-разметка переменных («переменная или константа?»), подтверждение батчем, биндинги per-host; параметризация обязательна для обобщения.
8. Память: lockfile, атомарные записи, schema_version + миграции, разделение определения (procedures/) и состояния (state/), index.json — производный артефакт.
9. Безопасность: deny-списки (rm, curl|sh, IEX, base64), запрет доступа к ~/.ssh, .env; вывод команд — untrusted (блоки с инструкцией не следовать), секреты маскируются; guard — defense-in-depth, не граница; новые процедуры исполняются только на P1.
10. Метрики: success rate по P-уровням, precision@k и MRR по golden set, false-negative классификатора, cost per procedure, latency P95.
11. Многопользовательность: только поле owner; роли/ревью — пост-MVP.
12. Офлайн: TF-IDF — первый класс (без внешних API); эмбеддинги и Ollama — пост-MVP.

## 6. Пост-MVP
Эмбеддинги (от ~300 процедур), полные эвристики обобщения, офлайн-чат (Ollama), wiki-экспорт, многопользовательность, телеметрийная верификация.

## 7. Оценка
MVP ≈ 35–45 ч. Порядок: 1 → 2 → 3 → 4 → 5 → 6. Безопасность (фаза 2) — до любого автономного исполнения.
